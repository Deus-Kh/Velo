## 1. Cryptographic core (`chats-client/src/shared/crypto`, `storage`, `chat`)

### 1.1 Primitives — sound

| Role | Primitive | Library | Where |
|---|---|---|---|
| Signatures | Ed25519 | `tweetnacl` | `identityKeys.ts:33`, `prekeys.ts:45`, `prekeyBundleVerify.ts:10` |
| DH | X25519 | `tweetnacl` | `x3dh.ts:60,67,72`, `dhRatchet.ts:117,124,127` |
| AEAD | XSalsa20-Poly1305, random 24-byte nonce | `tweetnacl` | `messageV2.ts:42,74` |
| Hash / HMAC / HKDF | SHA-256 | `@noble/hashes` | `kdf.ts`, `ratchetChain.ts:17-18`, `ratchetRoot.ts:15-20` |
| CSPRNG | `crypto.getRandomValues` via `react-native-get-random-values` | first import in `index.js:4` | correct ordering |

Chain KDF (`MK = HMAC(CK, 0x01)`, `CK' = HMAC(CK, 0x02)`) and root KDF (HKDF-SHA256, root key as salt) match Signal's constructions. No nonce reuse risk. `crypto-js` is a dependency with zero imports. `utf8.ts` is a hand-rolled codec whose decoder swallows failures (`utf8.ts:26`).

### 1.2 X3DH (`x3dh.ts`)

- DHs computed: `DH(EK_A, SPK_B)` (line 60), `DH(EK_A, OPK_B)` if present (67), `DH(IK_A, SPK_B)` (72). Missing: `DH(EK_A, IK_B)`. `bundle.identityDhPublicKey` is returned by the server (`keys.routes.ts:166`) and never used by the initiator.
- **Initiator is not authenticated.** `x3dhRespond` reads `initiatorIdentityDhPublicKey` from the `initPacket` (lines 130–133) and uses it directly. It is never compared with the server's record for `fromUserId`, never compared with the pinned identity, and the packet carries no signature.
- Bundle verification (`prekeyBundleVerify.ts:5-15`) verifies the SPK signature with the identity key delivered **in the same response**. No pinning against `trustedIdentities`. A server that swaps both keys passes the check.
- SPK signature covers only the raw 32-byte key (`prekeys.ts:45`): no key id, no timestamp, no domain tag.
- OPK: server consumption is atomic (`keys.routes.ts:158-162`). Client deletes the OPK secret (`x3dh.ts:124-127`) **before** the session is created (`sessionBootstrap.ts:38-49`); a failure between the two loses the conversation. If a session already exists, `ensureV2SessionFromIncoming` returns early (`sessionBootstrap.ts:36`) and the OPK secret is never deleted.
- OPK exhaustion: silent two-DH fallback (`x3dh.ts:65`). No marker, no signal.
- SPK is generated once and never rotated (`prekeys.ts:38-55`), `keyId = Date.now()` (line 42).

### 1.3 Double Ratchet — the DH step never runs

- `createSessionFromX3DH` (`sessionStore.ts:81-103`) gives **both** sides a fresh `DHs` and `DHrPublicKey: null`, and derives both chain keys from an HKDF split of the X3DH output (lines 57–79) mirrored by `isInitiator`.
- `decryptV2` (`messageV2.ts:108-115`): if `DHrPublicKey` is null, **adopt** the incoming `dhPub` without ratcheting; ratchet only if a later `dhPub` differs.
- `encryptV2` (`messageV2.ts:90`) always sends the session's existing `DHsPublicKey`. The only code that generates a new `DHs` is `applyDhRatchet` (`dhRatchet.ts:124`).
- Therefore: A sends with `DHs_A`; B adopts. B replies with `DHs_B`; A adopts. Neither ever changes `dhPub` again; `applyDhRatchet` never executes; `rootKey` is written once and never read. The protocol is two static HMAC chains. **No post-compromise security.**
- Consequences for other findings: the skipped-key wipe on ratchet (`dhRatchet.ts:150`) and the unread `header.pn` are currently unreachable.

### 1.4 Ratchet details

- No associated data: `nacl.secretbox(plainBytes, nonce, messageKey)` (`messageV2.ts:74`). `n`, `pn`, `dhPub` are malleable; nothing binds a ciphertext to a sender/recipient pair.
- Skip loop `while (nr <= targetN)` (`messageV2.ts:156-192`) runs on attacker-controlled `header.n`; `MAX_SKIP = 50` (line 23) only gates storing into the session map (line 173). Each iteration does two HMACs and an `await putV2MessageKey` (AsyncStorage write). Server validates only `typeof n === 'number' && n >= 0` (`setupSocket.ts:375-377`). `n = 1e9` hangs the device before authentication.
- State is mutated and keys are persisted before `secretbox.open` runs (lines 114, 163–187 vs 196).
- Replay: a message whose key is still in `skippedKeys` decrypts and is shown (line 135) before the key is deleted (136).
- `sessionTypes.ts:19-21` types `skippedKeys` by number; implementation keys by `${dhPub}:${n}` (`messageV2.ts:25-27`).
- `normalizeB64` is duplicated in `dhRatchet.ts:79`, `messageV2.ts:29`, `base64.ts:1`, `useChatE2EE.ts:98` and is applied to nonces and ciphertext, silently mutating malformed input.

### 1.5 Key storage

| Material | Store | Protection |
|---|---|---|
| Ed25519 identity, X25519 identity, SPK (pub+priv+sig), history master key | Keychain | OS-backed; **no** `accessible`/`accessControl` options (defaults; eligible for iCloud Keychain / device transfer) |
| Session state (`rootKey`, both chain keys, `DHsPrivateKey`, skipped keys) | AsyncStorage | **plaintext JSON** (`sessionStore.ts:17-30`) |
| One-time prekey secrets | AsyncStorage | plaintext (`oneTimePreKeys.ts:12`) |
| Per-message keys | AsyncStorage | `secretbox` under history MK (`v2MessageKeyStore.ts:23-44`); key name embeds `dhPub` and `n` in clear (line 15) |
| Trusted identity pins | AsyncStorage | plaintext, unauthenticated (`trustedIdentities.ts:19`) |
| Pending outgoing messages | AsyncStorage | **plaintext bodies** (`pendingMessageStore.ts:23-42`) |
| JWT | AsyncStorage | plaintext (`auth.store.ts:134`) |

`historyMasterKey.ts:11-12` claims AsyncStorage leaks do not reveal message keys; the plaintext chain keys in `sessionStore.ts` defeat that. Message keys are retained forever (`messageV2.ts:63,126,163,180`) and only deleted on manual reset (`useChatE2EE.ts:824`).

### 1.6 Trust and verification

- Safety number (`fingerprint.ts:14-36`): single SHA-256 over the two **Ed25519** keys sorted as base64 strings, first 30 hex chars. Omits the X25519 identity key used in the handshake; no iteration, no version byte, no user binding.
- The trust store is read only by `VerifyContactScreen.tsx:43` and `NewChatScreen.tsx:432` (a badge). No crypto or socket path consults it. "Verified" and "Identity changed" affect no decision.

### 1.7 Session lifecycle

- Both bootstrap paths return early when a session exists (`sessionBootstrap.ts:9,36`): peer reinstall and simultaneous initiation (glare) produce permanently mismatched sessions with no detection.
- History replay in `'live'` mode advances and persists the live ratchet (`useChatE2EE.ts:253-262`).
- Error classification by string matching, duplicated (`drainPendingMessages.ts:9-19`, `useChatE2EE.ts:81-91`).
- Dead but bundled v1 static-DH code: `messageCrypto.ts`, `sharedSecret.ts`, `keypair.ts`, `sharedSecretCache.ts` (only `.clear()` called), `protocolPolicy.ts` (never imported). `crypto/index.ts` is 0 bytes.
- No group, device, or fan-out concept anywhere (`sessionStore.ts:10` keys sessions by user pair; `socket/types.ts:14` one `toUserId`).

## 2. Server (`chats-server/src`)

### 2.1 Configuration and secrets
- `config.ts:7-8`: Mongo URI and JWT secret have hardcoded fallbacks; no `.env` exists, so they are the running values. The JWT fallback is a dictionary word; forging `{userId}` gives full impersonation over REST and WebSocket. `JWT_ALGORITHM` is declared and never used; `jwt.verify` (`middleware/auth.ts:16`) pins no `algorithms`.
- `tsconfig.json:24` `noEmit: true`; `package.json:10` `start: nodemon src/index.ts`; `nodemon` is a runtime dependency (line 22). No build, no process manager.
- No error middleware, no 404 handler; `NODE_ENV` unset; Express 5 forwards async rejections to `finalhandler`, which returns **stack traces with absolute paths** on any `CastError` (e.g. `GET /keys/bundle/notanid`). Socket handlers echo `e.message` to clients (`setupSocket.ts:575,625,691`).
- `cors({ origin: true, credentials: true })` on HTTP and Socket.IO (`index.ts:23,40`). `helmet()` defaults. No `trust proxy`.

### 2.2 Authentication
- Register (`auth.routes.ts:10-42`): email + username + password, no verification, **no password policy** (`change-password` enforces 8, line 76), check-then-insert race, case-sensitive usernames (`models/User.ts:6`), raw `{ username }` from body into the query (line 27).
- bcrypt cost 10 (line 31). `@ts-ignore` on both `jwt.sign` calls (33, 37). Token TTL 3h; no refresh route (client declares one at `endpoints.ts:6`), no revocation, no logout, `change-password` leaves old tokens valid (86–89).
- Socket auth verified once at connect (`setupSocket.ts:272-283`), never re-checked.
- **No rate limiting anywhere.** No lockout, no captcha.

### 2.3 Data model and metadata
- `Message` stores ciphertext plus the **cleartext ratchet header** `n`, `pn`, `dhPub` (`models/Message.ts:4-16`), the `initPacket` (18–27), `fromUserId` indexed (40), client timestamp used for sort (66) and pagination (`messages.routes.ts:24-36`).
- `Conversation.conversationId` is the sorted user pair (`utils/conversation.ts:2`); members hard-limited to 2 (`models/Conversation.ts:9-14`); free-form `lastMessagePreview` (18).
- **No TTL, no delete-after-delivery, no message deletion, no account deletion, no export.** Consumed OPKs and superseded SPKs are never removed.
- Presence and last-seen live in process `Map`s (`setupSocket.ts:252-253`); no Redis adapter; the service is capped at one process.

### 2.4 Key distribution (`keys.routes.ts`)
- Upload endpoints validate only `length >= 20` (15, 34, 71); prekey array items are not validated at all (110–116); the SPK signature is never verified server-side (90–94); identity keys are silently overwritable (26–29) with no history and no peer notification.
- `GET /keys/bundle/:userId` (134–177) consumes an OPK per call with no throttle and no relationship check: any account can drain any victim's pool; fallback to no-OPK is silent (173–175). No total-OPK cap.

### 2.5 Socket authorization
- `fromUserId` always comes from `socket.data.userId` (286, 412) — correct.
- `message:delivered` (588–597): `findByIdAndUpdate(serverMessageId)` with **no ownership check**; any user can mark any message delivered and trigger a forged receipt to its sender (613–619).
- `message:read` (630–686): trusts client `conversationId`; writes `unreadCounts` into an arbitrary conversation (653–660); derives the receipt target by splitting the attacker's string (669–670).
- `presence:subscribe` / `typing:*` (292–335): any userId, no relationship check.
- `message:send` (481–495): if the message has no `initPacket`, the server attaches the conversation's first stored one — a server-controlled session-establishment injection point. It also logs the full DTO including ciphertext on validation failure (347, 351, 362) and the full `initPacket` on every send (427–429). No ciphertext size cap.
- Ack means stored, not delivered (548); delivery is fire-and-forget (498); no undelivered-message endpoint; ordering keyed on the client clock.

### 2.6 Push (`push/firebase.ts`)
- Sends a `notification` payload with the **sender's username as title** (69) and `data` containing `conversationId` (the participant pair) and `fromUserId` (85–90). Body is constant — no content leak.
- Token pruning deletes a token on **any** failure including transient ones (107–109).
- Service account read from a JSON file in the server root (28–44).

### 2.7 Contact discovery (`users.routes.ts:173-199`)
- `q` optional → empty query dumps every user **with email**. Raw `$regex` from user input → ReDoS. `email` returned (195). Emails also exposed by `GET /conversations` (`conversations.routes.ts:12,38`).

## 3. Client application layer

### 3.1 Auth and session
- `login`/`register` (`auth.store.ts:130-132`, `155-157`) set `isLoading: true` then `await authApi.*` **outside** the try/finally; `Navigation.tsx:58` renders `null` while loading. A wrong password blanks the app until force-kill. `LoginScreen.tsx:34-36` and `RegisterScreen.tsx:36-38` have no try/catch, so no error is shown. Password minimum is 8 on login (`LoginScreen.tsx:86`) and 6 on register (`RegisterScreen.tsx:107`).
- `logout` (`auth.store.ts:199`) removes two AsyncStorage keys only. Sessions, message keys, OPK secrets, trust pins, pending plaintext, and all Keychain entries survive. `deleteAllSessionsForUser` (`sessionStore.ts:118`) is never called.
- Token expiry check commented out (`auth.store.ts:223-240`); 401 interceptor only logs (`http.ts:39-44`).
- Reinstall regenerates identity keys and uploads them; all server history becomes `[Encrypted]` forever (`useChatE2EE.ts:280,299,310`); "Reset secure session" deletes message keys (`useChatE2EE.ts:820-832`).

### 3.2 Transport
- `http.ts:6` and `socket.ts:5` hardcode `http://` to a bare AWS IP. `AndroidManifest.xml:15` `usesCleartextTraffic="true"`. `Info.plist:29-36` `NSAllowsArbitraryLoads=false` → **iOS cannot connect**. No `GoogleService-Info.plist`; `AppDelegate.swift` has no `FirebaseApp.configure()`; no `UIBackgroundModes`.

### 3.3 Push
- No `setBackgroundMessageHandler`, `onMessage`, `getInitialNotification`, `onNotificationOpenedApp`, or notifee event handler exists (grep across `src/`, `index.js`, `App.tsx`). Android background: OS-rendered from the server's `notification` payload. Foreground: socket-driven local notification only (`ChatListScreen.tsx:596-614`) whose "Message previews" toggle changes nothing (604–606) and whose title shows the sender username (603). Tap does nothing. `unregisterPushTokenFromServer` no-ops when push is disabled (`sync.ts:30-34`, `push.ts:127-133`), so a disabled-then-logged-out device keeps a live token.

### 3.4 Message flow
- Optimistic send with queue-first write (`useChatE2EE.ts:423-512`) is well built. Retry has no backoff and no cap. Ack promise has no timeout. History is refetched from the server on every open (`useChatE2EE.ts:562-608`, `PAGE_SIZE 30`); older pages decrypt in `stored_keys_only` mode (767). There is **no local message store**.

### 3.5 UX and code quality
- Zero `Alert.alert` (no confirmations on destructive actions). Zero accessibility props. No i18n. No onboarding. Offline composing is blocked (`ChatScreen.tsx:346,1069`) while the banner promises drafts are kept (369, 816). Read and delivered render identically for own bubbles (`MessageBubble.tsx:18-41`). Chat list refetches from three effects (`ChatListScreen.tsx:530,534,652-664`) and blanks behind a spinner on refresh (716–721). Archive is reachable only by an invisible pull-down zone.
- Dead code shipped: `components/ChatReset.tsx` (hardcoded ObjectIDs, `AsyncStorage.clear()`), `Navigation.tsx:14-32`, ~70 commented lines in `MainTabsScreen.tsx`, keyboard geometry logging on every keyboard event (`ChatScreen.tsx:688-694`). Release build: `enableProguardInReleaseBuilds = false` (`build.gradle:61`). Unused deps: `crypto-js`, `date-fns`, `uuid`, `@react-native/new-app-screen`, legacy `react-native-vector-icons`.
- Privacy: email is the login identifier and is shown on the chat list (`ChatListScreen.tsx:840,933,1027`); the "invite" is the raw Mongo ObjectID (`NewChatScreen.tsx:332,341`). No analytics SDKs. `PrivacyInfo.xcprivacy` is accurate today. `Info.plist:37-38` declares an empty location usage string (App Store rejection trigger).

## 4. Ranked findings

### 4.1 Security (all layers)
1. **Initiator identity unauthenticated; safety number omits the DH identity key; bundle trust unpinned** — `x3dh.ts:130-133`, `fingerprint.ts:14-21`, `prekeyBundleVerify.ts:5-15`.
2. **DH ratchet never executes → no post-compromise security** — `sessionStore.ts:81-103`, `messageV2.ts:90,108-115`, `dhRatchet.ts:124`.
3. **Cleartext HTTP and WebSocket** — `http.ts:6`, `socket.ts:5`, `AndroidManifest.xml:15`.
4. **Live secrets as config fallbacks with no `.env`; guessable JWT secret** — `chats-server/src/config.ts:7-8`.
5. **Release-keystore password tracked in a public repo** — `chats-client/android/gradle.properties:49-52`.
6. **Unbounded skip loop → remote device DoS before authentication** — `messageV2.ts:156-192`, `setupSocket.ts:375-377`.
7. **No header AD; ciphertext not bound to identities** — `messageV2.ts:74,90`.
8. **Session state, OPK secrets, pending plaintext, trust pins unencrypted at rest** — `sessionStore.ts:27-30`, `oneTimePreKeys.ts:12`, `pendingMessageStore.ts:41`, `trustedIdentities.ts:19`.
9. **Full user directory + email harvest + ReDoS** — `users.routes.ts:173-199`.
10. **No rate limiting; OPK pool drainable** — `auth.routes.ts:44`, `keys.routes.ts:134`.
11. **Socket authorization holes** (`message:delivered`, `message:read`, presence/typing) — `setupSocket.ts:292-335, 588-597, 630-686`.
12. **Server-side `initPacket` injection** — `setupSocket.ts:481-495`.
13. **Message keys retained forever (forward secrecy at rest surrendered)** — `v2MessageKeyStore.ts`, `messageV2.ts:63,126,163,180`.
14. **SPK never rotates; silent OPK-exhaustion fallback** — `prekeys.ts:38-55`, `x3dh.ts:65`.
15. **Logout leaves all key material on disk** — `auth.store.ts:199`.
16. **Push leaks sender username and participant pair to FCM** — `push/firebase.ts:69,85-90`.
17. **Stack traces returned to clients; permissive CORS** — no error middleware, `index.ts:23,40`.
18. **69 dependency advisories, 7 critical.**

### 4.2 Product-breaking
1. Wrong password blanks the app (`auth.store.ts:130-132`, `Navigation.tsx:58`).
2. iOS cannot connect (ATS) and has no Firebase config.
3. Push has no client handler; tap does nothing; preview toggle is a no-op.
4. Reinstall or "reset secure session" destroys all readable history; no backup.
5. Token expiry strands the user in a dead shell (no refresh, no forced logout).
6. Offline composing blocked despite the queue existing.
7. No confirmations, no accessibility, no i18n, no onboarding.
8. Client type-check fails; effectively zero tests.

### 4.3 What is genuinely good (keep)
Primitive and KDF choices; atomic OPK consumption; `fromUserId` from socket auth; message dedupe by unique index; queue-first optimistic send; Keychain for long-term keys; skeleton loaders, empty states, day separators, jump-to-latest pill, interactive back-swipe, full dark mode with density and surface options; minimal Android permissions; no analytics SDKs; no phone number required.
